# 前端能不能降到 Chrome 78？

> 结论先说：**不行。** 不是语法问题，是 **flex 布局的 `gap`**——全站 163 处，
> Chrome 84 才有。产物语法确实已经降到 78（`build.target`），但 CSS 早就把下限推到 84/108 了。
>
> 复现：`node tools/audit-chrome78.mjs` 与 `node tools/audit-gap-context.mjs`

---

## 一、先把三类东西分开

「支不支持某个 Chrome」不是一句话，得分三层看，因为**只有第一层能被构建工具降级**：

| 层 | 例子 | 能不能降级 | 不支持时什么现象 |
|---|---|---|---|
| **语法** | `?.` `??` `||=` class fields | ✓ esbuild 按 `build.target` 转写 | 构建期就报错，或产物是旧语法 |
| **JS 运行时 API** | `structuredClone` `.at()` `replaceAll` | ✗ 降级不了 | 调用处直接 `TypeError`（页面看着正常，一点就废） |
| **CSS 特性** | `gap` `:is()` `clamp()` `dvh` | ✗ esbuild 不处理 CSS | **整条声明被丢弃**，布局悄悄塌掉 —— 最难发现 |

`build.target = 'chrome78'` 只解决第一层。第二、三层要靠人肉对版本。

---

## 二、扫描结果

扫 `web/src/**`（76 个文件，`.vue` 拆 template/script/style 分别看）。

### 2.1 语法层：已经在 78

`build.target = ['chrome78','firefox78','safari13']`。
`?.` `??` 会被 esbuild 转成 `(_a = x) === null || _a === void 0 ? void 0 : _a.y`。
**这一层没问题。**

### 2.2 JS 运行时 API：全部通过

| API | 需要 | 用在 |
|---|---|---|
| `WebSocket` | Chrome 5 | 投屏 / 在线状态（4 文件） |
| `matchMedia` | Chrome 9 | 1 文件 |
| `createImageBitmap` | Chrome 50 | 1 文件 |
| `IntersectionObserver` | Chrome 51 | 1 文件 |
| `ResizeObserver` | Chrome 64 | 1 文件 |
| `navigator.clipboard` | Chrome 66 | 3 文件 |
| `getDisplayMedia` | Chrome 72 | 投屏（2 文件） |
| `File.text()` / `.arrayBuffer()` | Chrome 76 | 上传（11 文件） |

**没有一处用到 `structuredClone` / `.at()` / `replaceAll` / `Promise.any` / `Object.hasOwn`** ——
JS 侧完全能跑 78。

### 2.3 CSS：这里是墙

| 特性 | 需要 | 处数 | 不支持时 |
|---|---|---|---|
| **flex 容器的 `gap`** | **Chrome 84** | **163** | **子元素挤在一起，全站间距消失** |
| `min()` / `max()` / `clamp()` | Chrome 79 | 13 | 响应式尺寸失效（`min(1100px, 92vw)` 整条丢） |
| `inset: 0` 简写 | Chrome 87 | 5 | 遮罩层不铺满屏幕 |
| `scrollbar-gutter: stable` | Chrome 94 | 1 | 滚动条出现时布局横向跳动 |
| `height: 100dvh` | Chrome 108 | 2 | 代码练习页高度失效 |

注意区分：**grid 容器里的 `gap` 是 Chrome 57**（没问题）。真正的问题是 flex。
`node tools/audit-gap-context.mjs` 的统计：

```
grid 容器里 gap    17 处   ← Chrome 57，安全
flex 容器里 gap   163 处   ← Chrome 84，78 上全失效
未声明 display      5 处   ← 继承父级，多为 flex
```

163 处里包括 `.row` / `.pagehead` / `.card-head` / `.side` / `.modal-head` 这些**骨架类**，
不是局部样式——意味着 `gap` 一失效，是整站布局垮掉，不是某一块难看。

---

## 三、真实下限是多少

按「要改多少代码」分三档：

| 方案 | 下限 | 要改什么 |
|---|---|---|
| **现状（什么都不改）** | **Chrome 108** | 无（`100dvh` 是最高的那项） |
| 改 8 处小 CSS | **Chrome 84** | `100dvh`×2 加 `100vh` fallback、`scrollbar-gutter`×1 删掉、`inset:0`×5 拆成 `top/right/bottom/left` |
| 想低于 84 | 不现实 | 163 处 flex `gap` 得改成 margin 方案，等于重写布局 |

**`gap` 在 flex 容器里就是硬底：84。**

---

## 四、那 `build.target = chrome78` 怎么办

三种选择：

### A. 保持 78（当前）
- 成本：产物比 109 大 **0.6KB**（实测 4364.4 vs 4363.8 KB，0.01%）
- 好处：语法层面确实能跑 78，万一机房有 78~83 的机器，**JS 不会崩**（但 CSS 会难看）
- 风险：**给人"支持 78"的错觉**——真拿 78 去开会发现布局全乱

### B. 抬到 `chrome108`（与真实能力对齐）★ 推荐
- 收益：配置与实际能力一致，不再自欺；产物略小
- 前提：`MIN_CHROME` 和 `check-compat.mjs` 的基线一起改成 108，否则兜底页判断与实际不符
- 代价：那 0.6KB 之外没有别的代价

### C. 先修那 8 处 CSS，再定 84
- 收益：真的能在 84~108 的老机器上用（不只是"JS 不崩"）
- 前提：机房确认最低版本确实是 84 以上

> **关键：无论选哪个，`build.target` / `index.html` 的 `MIN_CHROME` / `check-compat.mjs` 的基线
> 这三处必须同步改。** 只改一处会出现「产物白屏但兜底页认为浏览器合格」——
> 老师看到的是一片空白，没有任何提示。

---

## 五、结论

**降到 Chrome 78 不可行**，卡在 163 处 flex `gap`（Chrome 84）。

- JS 侧：完全可以（最高只要 76）
- 语法侧：已经降级到位（target=chrome78）
- **CSS 侧：这就是下限，163 处 flex gap 决定了不可能低于 84**

当前「基线 109 + target 78」的组合里，**109 是准的**（真实不改代码的下限是 108，
差的 1 个版本来自 2 处 `100dvh`），而 **78 只是个语法余量，不代表真能跑**。

## 附：复现与巡检

```bash
node tools/audit-chrome78.mjs      # 按 Chrome 78 扫 JS API + CSS，列出 blocker
node tools/audit-gap-context.mjs   # 单独看 gap 用在 grid 还是 flex（结论的关键）
node tools/check-compat.mjs        # 现有基线体检（防回退，盯 build.target 与 dist）

# 想看某一项的具体行，直接 grep：
#   grep -rn "clamp(" web/src
#   grep -rn "inset: 0" web/src
#   grep -rn "100dvh" web/src
```

前两个是**分析工具**，用途是回答「能不能降到某个版本」；
日常防回退还是靠 `check-compat.mjs`（它只认当前基线）。

改 CSS 时注意：`gap` 是安全的（只要容器是 grid），**但别往 flex 容器里新加 `gap`** —— 那会把下限悄悄推到 84。
