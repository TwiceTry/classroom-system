## 二、这一轮已修的真问题

**`api.js` 的错误信息会全变成 `[object Object]`**

新后端错误体是 `{ error: { code, message } }`（对象），而旧代码直接：

```js
throw new StatusError(new Error(data.error || ...))   // ← data.error 是对象
```

→ 页面上所有接口报错都显示 `[object Object]`，**等于错误信息全丢**。

已修：`errorMessage()` 同时认「旧版字符串」和「新版对象」，并把 `error.code` / `error.details` 挂到 Error 上（前端可按 code 分支，不用匹配中文）。`openDoc()` 里同样的坑也一并修了。

## 三、值得做但**没在本轮仓促做**的（附方案）

### P1 · `PgWorkbench.vue` 1881 行（script 960）

现状：文件树 + 代码编辑器 + 实时预览 + 保存/提交/同步，全在一个组件里。

按「谁会一起变」拆：

| 拆出 | 内容 | 为什么这样拆 |
|---|---|---|
| `composables/useFileTree.js` | 目录展开/选中/刷新 | 只有它关心「树」的结构 |
| `composables/useCodeEditor.js` | CodeMirror 实例、内容脏标记、保存 | 编辑器生命周期独立，卸载要销毁 |
| `composables/usePreview.js` | iframe 预览、pgsync 轮询 | 与编辑内容通过显式参数交互 |
| `components/CodeWorkbench/*` | 三个子组件只负责渲染 | 父组件变成编排者 |

风险：**中高**（编辑器实例与 iframe 生命周期容易出内存泄漏），需要真浏览器回归。

### P1 · `Assignments.vue` / `Projects.vue` / `Classes.vue`（1311 / 1196 / 1290 行）

三者共享同一套模式：列表 + 详情抽屉 + 批量操作 + 15 次左右的 API 调用。

抽一个 `composables/useApiList.js`：

```js
const { items, loading, error, reload, create, remove } = useApiList(
  () => '/api/assignments?itemKey=' + itemKey.value
)
```

预期：每个页面少 100~200 行重复的 loading/error/retry 骨架。

风险：**低**（纯数据层），但要改 4 个页面 —— 建议**一次只改一个页面**，跑通再推下一个。

### P2 · 列表虚拟化

`Attendance.vue`（8 处 v-for）在 60 人班级下**并不卡**；真正的长列表是「记分记录」（一学期可达上千条）。

→ 优先级要放在「记分记录抽屉」上，用 `v-for` + 高度固定的窗口化即可，不必引入第三方库。
风险：**低**，收益中等。**过早优化其他列表是浪费。**

### P2 · `Scheme.vue` 18 处 v-for / 1251 行

方案编辑器是「结构化的嵌套表单」（考核项 → 等级/维度/规则参数），天然层数多。
建议用 `v-for` 的 key 稳定性 + `shallowRef` 处理大的方案对象，而不是拆分组件（拆开反而要在父子间传一堆回调）。
风险：**低**，但收益也有限（一次只编一个方案）。

## 四、结论

- 前端的**地基是好的**：唯一的网络出口（`api.js`）、统一的 Bearer、401 回调、下载/打印都有封装。
- 真正的问题是**三个巨型页面**把「数据获取 + 业务规则 + 渲染」混在一起，改动一处要读 1000 行。
- 本轮只做了**零风险的**一处修复（错误体兼容），大文件拆分留作**独立一轮**：按「一次一个页面、跑通再下一个」的节奏推进，避免半新半旧。

> 判断依据：把 1881 行的编辑器工作台在预算末尾仓促拆一半，产生的风格割裂和回归风险，
> 大于它带来的可读性收益。宁可留一份明确的方案，下一次完整做完。
